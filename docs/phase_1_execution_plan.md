# خطة تنفيذ المرحلة 1: البنية التحتية للتطبيق

هذه خطة مستقلة لتنفيذ المرحلة 1 من [`execution_plan.md`](./execution_plan.md).
تقسم العمل إلى مراحل فرعية متتابعة؛ لا تبدأ المرحلة الفرعية التالية قبل اجتياز
معيار الخروج للمرحلة الحالية، إلا إذا ذُكر اعتماد قابل للفصل صراحةً.

## سجل التقدم

**آخر تحديث:** 21 أكتوبر 2026  
**الحالة العامة:** التنفيذ جارٍ؛ لم يُجتز بعد معيار خروج أي مرحلة فرعية.

أُنشئت مسودة تنفيذ تغطي ملفات ومكونات البنود 1.1–1.11: نقطة دخول ووجهات
أولية، نماذج Typed، SQLite ومستودعات، خدمات تشغيل الكود والاختبارات، نقل وعميل
LSP، فهرسة مساحة العمل، إعدادات اللغة والمظهر، مزودات الحالة وتركيب الاعتماديات،
وموارد أولية. هذا يسجل نطاق الكود الموجود فقط، ولا يعني اكتمال أي بند قبل تشغيل
اختباراته واجتياز معيار خروجه.

**المتبقي قبل اعتماد المرحلة 1:**

- تنسيق الملفات والتحليل الساكن واختبارات النماذج والتخزين والخدمات والواجهات.
- اختبار عميل LSP على النقل الوهمي وعلى executable فعلي؛ لا يوجد executable
  مبني في مسار `gdscript_lsp/build/` حاليًا.
- عقد الخادم الحالي لا يعلن حتى الآن امتدادي
  `experimental.gdscriptUpdateWorkspaceFiles` و
  `experimental.gdscriptSearchWorkspaceText` اللذين يشترطهما العميل؛ يجب حسم
  العقد وإثباته قبل اعتبار مزامنة الفهرس والبحث متكاملين.
- التحقق النهائي بـ `flutter analyze` و`flutter test`، وتشغيل التطبيق على الهدف
  المدعوم، وتوثيق القيود الفعلية.

## الهدف والنطاق

تجهيز أساس التطبيق القابل للاختبار: بنية المجلدات، النماذج، التخزين المحلي،
الخدمات، عميل LSP وفهرس مساحة العمل، إعدادات اللغة والمظهر، التوجيه، وإعداد
أصول المحتوى. هذه المرحلة **لا** تنشئ الدروس أو التمارين الفعلية، ولا تنفذ
شاشات المنتج النهائية أو المحرر المرئي؛ تقتصر الشاشات على وجهات أولية تكفي
للتحقق من التوجيه.

### شروط البدء

- المرحلة 0 مكتملة، واختبارات `gdscript_engine` و`gdscript_lsp` وعقد فهرسة
  مساحة العمل موثقة.
- مستودع `gdscript_engine` متاح في مسار الاعتماد المحلي المحدد في
  `pubspec.yaml`.
- يجري العمل على فرع نظيف أو تُحفظ التغييرات القائمة بوضوح؛ لا تستبدل تغييرات
  `pubspec.yaml` أو `pubspec.lock` الموجودة لمجرد بدء الخطة.

### مبادئ التنفيذ

1. الحفاظ على فصل الواجهة والمنطق ومصادر البيانات؛ لا تستدعِ قاعدة البيانات أو
   المحرك أو عملية LSP مباشرةً من الواجهات.
2. لكل اعتماد خارجي واجهة يملكها التطبيق واختبار مناسب؛ لا تُخفَ أخطاء التخزين
   أو التشغيل أو النقل بنتائج نجاح شكلية.
3. ملفات المنهج والأمثلة والشيفرة تبقى كما هي دون ترجمة؛ تُترجم النصوص البشرية
   عبر `LocalizedText` أو ملفات ARB بحسب موضعها.
4. إدارة مساحة العمل والفهرسة مسؤولية التطبيق. لا يُطلب من خادم LSP اكتشاف
   الملفات أو قراءتها من القرص.
5. التشغيل المحلي لخادم LSP عبر subprocess متاح فقط للأهداف التي يدعمها
   executable؛ لا يُفعّل على Android أو iOS أو الويب دون حل نقل/استضافة منفصل.
6. لا تضف اعتماداً أو طبقة تجريد إلا عند حاجة مثبتة، وسجّل قراراً واضحاً حول
   ملكية دورة حياة كل خدمة.

## 1.1 إنشاء الهيكل وتهيئة التطبيق

**يعتمد على:** شروط البدء فقط  
**الناتج:** نقطة دخول رفيعة، هيكل المجلدات، وثوابت ومرافق عامة أولية.

### المهام

- إضافة `lib/app.dart` ونقل تركيب `MaterialApp` إليه؛ إبقاء `lib/main.dart`
  نقطة دخول لا تحتوي منطق واجهة أو خدمات.
- إنشاء المجلدات الأساسية المتفق عليها:
  - `lib/core/constants/`, `extensions/`, `utils/`
  - `lib/data/models/`, `repositories/`, `sqlite/`
  - `lib/logic/providers/`, `services/`
  - `lib/ui/screens/`, `widgets/`, `layouts/`
  - `lib/l10n/`
- إضافة الثوابت العامة وثوابت GDScript التي لها استخدام فعلي، وأدوات المنصة
  والتجاوب فقط إذا احتاجتها مراحل لاحقة.
- إبقاء ملفات الثيم الحالية في `lib/core/theme/` وتوسيعها بدلاً من استبدالها.
- إضافة اختبارات smoke لنقطة الدخول وبناء الشجرة بعد نقلها.

### معيار الخروج

- يعمل التطبيق من نقطة الدخول الجديدة على بيئة التطوير الحالية.
- الهيكل يتبع المسؤوليات الفعلية؛ لا تُنشأ ملفات placeholder فارغة لمجرد
  مطابقة شجرة مقترحة.
- `flutter analyze` واختبارات smoke تمر.

## 1.2 تثبيت نماذج المجال والعقود

**يعتمد على:** 1.1  
**الناتج:** نماذج مكتوبة النوع وقابلة للتحويل من/إلى JSON مع تحقق مدخلات واضح.

### النماذج

- `LocalizedText`
- `Curriculum` و`Unit`
- `Lesson`
- `Exercise` و`ExerciseTestCase` و`ExerciseType`
- `UserProgress` و`LessonProgress` و`LessonStatus`
- `AppSettings` واختيار اللغة والمظهر

### المهام

- تعريف الحقول المطلوبة والاختيارية والقيم الافتراضية بما يتوافق مع مخططات
  المرحلة 1 في الخطة الرئيسية.
- توفير `fromJson` و`toJson` صريحين للنماذج التي ستُقرأ من الأصول أو تُخزّن
  محلياً.
- استخدام أنواع Dart محددة، ونسخ غير قابلة للتعديل للقوائم/الخرائط عند الحاجة؛
  لا تستخدم `dynamic` في واجهات المجال العامة.
- تحديد سلوك الحقول الناقصة أو غير الصالحة برسائل خطأ قابلة للتشخيص، وعدم
  استبدال البيانات التالفة بقيم صحيحة ظاهرياً.
- عدم ترجمة معرفات البيانات أو code أو مخرجات التنفيذ.

### الاختبارات

- round-trip JSON للنماذج المركبة وحالات null والقيم الافتراضية المسموح بها.
- رفض أنواع JSON الخاطئة والمعرفات أو القيم المطلوبة المفقودة.
- التأكد من اختيار `LocalizedText.resolve` للغة المطلوبة، مع fallback موثق
  للغات غير المدعومة.

### معيار الخروج

- النماذج متوافقة مع أمثلة JSON موثقة وثابتة في الاختبارات.
- التحليل الساكن واختبارات النماذج تمر دون تحويلات غير آمنة.

## 1.3 تأسيس قاعدة البيانات والترحيلات

**يعتمد على:** 1.2  
**الناتج:** فتح قاعدة البيانات وإصدار مخطط قابل للترقية واختبارات تخزين فعلية.

### المهام

- توحيد المسار المقترح إلى `lib/data/sqlite/` أو توثيق أي اختلاف عن
  `lib/data/database/` قبل إنشاء الملفات.
- تنفيذ مالك واحد لدورة حياة اتصال SQLite، مع فتح كسول، إغلاق صريح للاختبارات
  والإيقاف، والتعامل الواضح مع فشل فتح الملف.
- إنشاء مخطط أولي لـ `user_progress` و`lesson_progress` و`earned_badges`
  وفق النماذج المعتمدة.
- إضافة رقم إصدار للمخطط وآلية migrations متسلسلة؛ لا تعتمد على إنشاء الجداول
  وحده لتحديث قواعد بيانات أقدم.
- استخدام معاملات وبيانات مُعلّمة parameters للعمليات ذات القيم المتغيرة.
- تحديد platform support لـ `sqlite3` و`path_provider` من حزم المشروع الفعلية؛
  لا تفترض دعم الويب أو الأجهزة دون تحقق.

### الاختبارات

- إنشاء قاعدة مؤقتة، تشغيل التهيئة أكثر من مرة دون فقد البيانات، والتحقق من
  الجداول والفهارس والقيود.
- اختبار الترحيل من إصدار سابق إلى الحالي، واختبار الإغلاق وإعادة الفتح.
- اختبار فشل المسار/الفتح، والتأكد من ظهور الخطأ بدلاً من إنشاء قاعدة بديلة
  صامتة.

### معيار الخروج

- يمكن إنشاء قاعدة جديدة وترقيتها وإعادة فتحها مع ثبات البيانات.
- كل تغيير مخطط لاحق يملك migration واختباراً مقابلاً.

## 1.4 تنفيذ المستودعات ومصادر البيانات

**يعتمد على:** 1.2 و1.3  
**الناتج:** واجهات تخفي تفاصيل SQLite والأصول وتقدم عمليات مجال واضحة.

### المستودعات

- `curriculum_repository.dart`: يقرأ فهرس المنهج من AssetBundle عند إضافته
  لاحقاً، ويفك JSON إلى نماذج typed. في هذه المرحلة يُختبر بخدمة أصول وهمية؛
  لا تُنشأ دروس فعلية.
- `progress_repository.dart`: يقرأ ويكتب تقدم المستخدم والدروس بعمليات
  ذرية ومتوافقة مع المخطط.
- `settings_repository.dart`: يحفظ اللغة والمظهر ويستعيدهما، مع قيمة افتراضية
  عربية و`ThemeMode.system` عند عدم وجود إعداد سابق.
- `workspace_repository.dart`: يملك جذر مساحة العمل وبيانات الملفات المفهرسة
  محلياً وفق سياسة التطبيق؛ لا يخلط التخزين المحلي برسائل LSP.
- `syntax_reference_repository.dart`: تعريف واجهة القراءة ونتائج فارغة صريحة
  إلى أن تُضاف بيانات المرجع في مرحلة المحتوى.

### المهام والاختبارات

- تمرير قاعدة البيانات/مصدر الأصول عبر constructor أو واجهة محددة؛ تجنب
  singleton مخفي داخل المستودعات.
- اختبار repository contract باستخدام SQLite مؤقتة، واختبار قراءة الأصول عبر
  AssetBundle بديل.
- اختبار حفظ الإعدادات واستعادتها عبر إعادة إنشاء المستودع.
- إرجاع أخطاء محددة عند JSON تالف أو فشل I/O أو تعارض معرف؛ لا تتجاهل
  الاستثناءات ولا تحولها إلى قوائم فارغة.

### معيار الخروج

- الخدمات والمزودات لا تحتاج إلى SQL أو AssetBundle مباشرة.
- عمليات القراءة والكتابة الأساسية واختبارات الفشل تمر.

## 1.5 تنفيذ خدمة تشغيل الكود

**يعتمد على:** 1.2  
**الناتج:** واجهة مستقرة بين التطبيق و`gdscript_engine`.

### المهام

- تنفيذ `CodeRunnerService` بملكية واضحة لـ `GDScriptEngine` و`dispose`.
- تعريف `CodeRunResult` typed يشمل النجاح، المخرجات، رسالة الخطأ،
  diagnostics، مدة التنفيذ وعدد التعليمات إذا كانت متاحة في واجهة المحرك.
- تحويل نتيجة المحرك دون إسقاط diagnostics أو إخفاء سبب الفشل.
- إبقاء التشغيل منفصلاً تماماً عن LSP؛ لا يبدأ تشغيل الكود عملية الخادم.
- اعتماد حدود التنفيذ المتاحة فعلياً في إعدادات المحرك وعدم الادعاء بمهلة
  إيقاف/عزل لا يوفرها المحرك.

### الاختبارات

- `print("hello")` يعيد نجاحاً والمخرج `["hello"]`.
- كود غير صالح يعيد نتيجة فشل مع رسالة/تشخيصات فعلية.
- تشغيل متكرر يتحقق من عدم خلط المخرجات أو الحالة بين التنفيذات، وفق سلوك
  المحرك الحالي.
- اختبار تحرير المورد عند الإغلاق.

### معيار الخروج

- لا تستدعي الواجهة المحرك مباشرة؛ كل التشغيل يمر عبر الخدمة.
- النجاح والفشل والمخرجات مرئية بدقة في النتيجة.

## 1.6 تنفيذ خدمة اختبار التمارين والتلميحات

**يعتمد على:** 1.2 و1.5  
**الناتج:** مقارنة نتائج حالات الاختبار وعقد مستقل للتلميحات.

### المهام

- تنفيذ `TestRunnerService` لتشغيل كل حالة مع `setupCode` عند وجوده، وربط
  النتيجة بحالة الاختبار، وعدد الناجح/الإجمالي.
- تطبيق `ignoreWhitespace` و`ignoreCase` كلٌّ على حدة وبالترتيب الموثق؛ لا
  تجعل أحد الخيارين يفعّل الآخر.
- تحديد هل المقارنة على كل أسطر الإخراج مجتمعة أم على الأسطر المنفصلة، وتوثيق
  السلوك واختباره قبل اعتماده.
- إيقاف المعالجة أو متابعة الحالات عند فشل تشغيل حالة واحدة وفق سياسة صريحة؛
  الافتراضي المقترح تشغيل جميع الحالات وإظهار خطأ كل حالة على حدة.
- إضافة `HintService` بسيط يعيد التلميح التالي المتاح دون كشف الحل، أو تأجيله
  إذا لم يكن له سلوك مطلوب في هذا النطاق.

### الاختبارات

- حالات نجاح وفشل للمخرجات، ومسافات الأسطر، وحساسية الأحرف.
- `setupCode` مع كود المستخدم، وتمرين بلا حالات اختبار، وفشل المحرك.
- المحافظة على ترتيب الحالات وعدم احتساب الفشل كنجاح.
- تحقق من عدد التلميحات وحدود الانتقال إلى التالي.

### معيار الخروج

- المقارنة حتمية ومغطاة بالحالات الحدية، ولا تُحوّل أخطاء التنفيذ إلى نجاح.

## 1.7 بناء عميل LSP وعزل النقل

**يعتمد على:** 1.1 ونتائج المرحلة 0  
**الناتج:** عميل LSP typed يملك تشغيل الخادم وطلبات البروتوكول ودورة الحياة.

### المهام

- تعريف واجهة نقل قابلة للاستبدال تخفي `Process` وstdin/stdout عن خدمات
  المحرر. تنفيذ نقل subprocess لـ Linux/macOS/Windows المدعومة فقط.
- إدارة الإطارات `Content-Length` وUTF-8 والرسائل المتزامنة/المتعددة دون خلط
  الاستجابات حسب ترتيب الوصول؛ ربط كل response بمعرف الطلب.
- تنفيذ `initialize` و`initialized` و`shutdown` ثم `exit` بترتيب LSP، وإغلاق
  stdin والاشتراكات والعملية بصورة حتمية.
- توفير طلبات وإشعارات typed للخدمات اللازمة: مزامنة المستند، diagnostics،
  completion، semantic tokens، hover، signature help، definition/references،
  folding، selection/document highlight، formatting، workspace symbols،
  والبحث النصي المخصص.
- إتاحة إلغاء الطلب حيث يسمح البروتوكول، وإظهار أخطاء بدء العملية وانقطاع
  النقل وJSON-RPC والخروج غير المتوقع مع السياق المناسب.
- عدم تسجيل نصوص الكود أو الأسرار. لا تُرجع نتائج نجاح افتراضية عند غياب
  executable أو تعطل النقل.
- تعريف factory اختيار executable بحسب النظام والمعمارية، والتحقق منها قبل
  التشغيل؛ أعِد حالة عدم الدعم على Android/iOS/web بدلاً من محاولة Process.
- اختبار dispatcher مع transport وهمي مستقل عن نظام التشغيل، ثم smoke على
  executable المرحلة 0.

### اختبارات القبول

- اختبار إطارات مجزأة ومتعددة، UTF-8، استجابات متزامنة، JSON-RPC errors،
  الإلغاء، الإغلاق، وفشل التشغيل/انقطاع stdout.
- اختبار تكامل فعلي `initialize → open/change document → request/notification
  → shutdown → exit`.
- اختبار أن كل طلب يستخدم capability معلنة وموجودة بالخادم فقط.

### معيار الخروج

- العميل لا يعتمد على عناصر Flutter، ونقل subprocess محصور في adapter المنصة.
- عملية الخادم لا تبقى معلقة بعد shutdown أو عند فشل initialize.

## 1.8 تنفيذ مستودع مساحة العمل وفهرستها

**يعتمد على:** 1.3 و1.4 و1.7  
**الناتج:** اكتشاف التطبيق للملفات وإبقاء فهرسه متزامناً مع الخادم.

### المهام

- تنفيذ `WorkspaceIndexService` فوق `workspace_repository` وواجهة LSP، مع
  اختيار جذر مساحة العمل وإزالته.
- تحديد سياسة واضحة لاكتشاف `.gd` والاستثناءات: المجلدات المولدة والمخفية
  والروابط الرمزية وحدود الملفات والصلاحيات. لا تُرسل ملفات خارج الجذر أو
  ملفات غير مسموح بها.
- بناء snapshot أولي صريح بعد اختيار مساحة العمل، ثم إرسال upserts عند الإنشاء
  أو التغيير والحذف عند الإزالة إلى عقد
  `gdscript/updateWorkspaceFiles`.
- جعل تحديث الدفعة قابلاً للاستعادة: فشل النقل لا يعلّم snapshot المحلي بأنه
  وصل للخادم؛ عند عودة الاتصال أرسل مزامنة كاملة أو delta موثقاً.
- إرسال `didOpen`/`didChange` للمستند المفتوح، وجعل النص المفتوح أحدث من
  snapshot القرص؛ عند الحفظ حدّث الفهرس بما يطابق المحتوى، وعند الإغلاق أعد
  المزامنة/احتفظ بآخر snapshot صالح.
- ضبط حجم الدفعات وفق حدود الخادم الحالية (10,000 ملف، 1 MiB لكل ملف)، مع
  رسائل خطأ قابلة للعرض عن ملفات مرفوضة أو غير مقروءة.
- عدم إنشاء شاشة إدارة المشروع النهائية هنا؛ يمكن اختبار الخدمة بواجهة الملفات
  ومزوّد اختيار مجلد وهميين.

### الاختبارات

- اكتشاف أولي وإضافة وتعديل وحذف، مجلدات مستثناة، ملف خارج الجذر، وامتدادات
  غير `.gd`.
- ملفات غير قابلة للقراءة، ملف أكبر من الحد، فشل أثناء دفعة، وإعادة المزامنة
  بعد إعادة تشغيل الخادم.
- التحقق من وصول التحديثات إلى البحث بالرموز والنص والتعريفات/المراجع.

### معيار الخروج

- مالك وحيد للاكتشاف والفهرسة هو التطبيق؛ الخادم يستقبل التغييرات ولا يمسح
  القرص.
- لا يفقد النظام حالة الملفات عند خطأ نقل، ولا يعرض نتائج index قديمة كأنها
  محدثة.

## 1.9 تنفيذ إعدادات اللغة والمظهر والتعريب

**يعتمد على:** 1.2 و1.4  
**الناتج:** إعدادات محفوظة ومطبقة فورياً، وواجهة عربية/إنجليزية اتجاهها صحيح.

### المهام

- إعداد `l10n.yaml` وملفات ARB العربية والإنجليزية، وتفعيل `flutter: generate`
  وتضمين delegates وsupported locales.
- توفير مجموعة مفاتيح أولية لكل النصوص التي تظهر في shell وواجهات المرحلة
  الأولية ورسائل الإعدادات والحالات والأخطاء؛ لا تضع نصوص الواجهة مباشرة في
  Widgets.
- تهيئة اللغة الافتراضية إلى العربية والمظهر إلى `ThemeMode.system`، وقراءة
  القيم المخزنة من `SettingsRepository` قبل عرض shell لتفادي وميض لغة/مظهر
  خاطئ.
- تطبيق `locale` واتجاه RTL للعربية وLTR للإنجليزية. لا تفرض RTL على محرر
  الشيفرة أو stdout لاحقاً.
- إضافة نمط فاتح وداكن متسقين مع theme files الحالية؛ تحديث الاختيار فوراً
  وحفظه، ومعالجة فشل الحفظ دون الإيحاء بنجاح دائم.
- إضافة ألوان المحرر في theme منفصل عن ألوان الواجهة.

### الاختبارات

- اختبار البداية الافتراضية واستعادة الإعدادات وتحديث locale/theme دون إعادة
  تشغيل التطبيق.
- اختبار directionality للغتين مع التأكد من بقاء مساحة code LTR.
- التحقق من تطابق مفاتيح ARB وعدم وجود مفاتيح ناقصة أو نصوص مرئية غير مترجمة.

### معيار الخروج

- العربية هي الاختيار الأول، واللغة والمظهر يستمران بعد إعادة تشغيل التطبيق.
- لا تظهر أخطاء توليد localization أو مفاتيح مفقودة في `flutter analyze`.

## 1.10 إضافة مزودات الحالة وتركيب الاعتماديات

**يعتمد على:** 1.4 إلى 1.9  
**الناتج:** حالة التطبيق قابلة للمراقبة والاختبار، ونقطة تركيب واحدة للاعتماديات.

### المهام

- تنفيذ providers المطلوبة فقط: curriculum، lesson، exercise، progress،
  app settings؛ لا تنشئ provider بلا حالة أو استهلاك محدد.
- استخدام نمط متسق مع اعتماد المشروع: Provider لحالة الواجهة التفاعلية؛
  واستخدام `get_it` لتسجيل الخدمات طويلة العمر فقط إذا كان ذلك هو الاختيار
  المعتمد. لا تكرر تسجيل الخدمة نفسها في locator وProvider دون سبب موثق.
- إنشاء نقطة تهيئة غير متزامنة تبني قاعدة البيانات والمستودعات والخدمات ثم
  تعرض التطبيق؛ تُمرر الاعتماديات للمكونات عبر constructors.
- تعريف حالة loading/error/data للمصادر غير المتزامنة، مع رسائل/أخطاء واضحة
  وعدم استبدال فشل التحميل ببيانات فارغة على أنه نجاح.
- تحديد من يغلق قاعدة البيانات والمحرك وعميل LSP عند إنهاء التطبيق أو تبديل
  مساحة العمل.

### الاختبارات

- اختبار كل provider مع repositories وهمية أو SQLite مؤقتة؛ تضمين النجاح
  والتحميل والفشل والتحديث.
- اختبار ترتيب التهيئة، فشل قاعدة البيانات، وفك الموارد مرة واحدة فقط.
- التأكد من عدم اعتماد طبقة البيانات أو الخدمات على BuildContext.

### معيار الخروج

- لكل خدمة مالك دورة حياة واحد، وتركيب التطبيق قابل للاستبدال في الاختبارات.
- لا توجد متغيرات global قابلة للتغيير أو اعتماديات مخفية غير موثقة.

## 1.11 إضافة التوجيه وموارد المحتوى والتحقق النهائي

**يعتمد على:** 1.1 إلى 1.10  
**الناتج:** shell ابتدائي قابل للتنقل وإعداد manifest الأصول ومعايير قبول المرحلة.

### المهام

- إضافة `lib/app.dart` routes أو `onGenerateRoute` للمسارات المتفق عليها:
  `/`, `/path`, `/settings`, `/onboarding`، ومسار الدرس بمعرف. استخدم حلاً
  موجوداً قبل إضافة مكتبة توجيه جديدة.
- إنشاء وجهات أولية صغيرة فقط لاختبار التوجيه، مع عناوين مترجمة؛ لا تبنِ
  واجهات المرحلة 3 هنا.
- اختبار المسارات الثابتة والديناميكية ومعرف الدرس المفقود/غير الصالح والرجوع.
- إنشاء بنية مجلدات أصول المنهج ومرجع الصياغة وإضافة asset paths إلى
  `pubspec.yaml` عند الحاجة. أضف فهرس JSON فارغاً صالحاً أو fixture اختبارية
  فقط إذا تطلب عقد المستودع ذلك؛ لا تضف محتوى المرحلة 2.
- كتابة README قصيرة فقط إذا احتاج تشغيل التطبيق أو إعداد مسار المحرك/LSP
  توضيحاً إضافياً؛ لا تُنشئ مستندات تخطيط أخرى.
- تشغيل التحقق النهائي: `flutter pub get`, `flutter analyze`, `flutter test`.
  اختبر تشغيل الخدمة/العملية على targets المدعومة فقط، ولا تدّعِ تغطية منصات
  لم تُختبر.

### معيار الخروج

- جميع معايير قبول المرحلة 1 في الخطة الرئيسية متحققة باختبارات أو تحقق قابل
  لإعادة التنفيذ.
- يمكن فتح التطبيق والتنقل بين الوجهات الأولية واستعادة الإعدادات.
- موارد المنهج مسجلة وقابلة للتحميل، لكن لا يوجد محتوى تعليمي فعلي سابق
  لأوانه.
- توثيق القيود والحالات غير المدعومة متوافق مع السلوك الحقيقي.

## سجل القرارات المطلوب أثناء التنفيذ

قبل اعتماد كل قرار مؤثر، سجّل القرار في وصف PR أو سجل هندسي قائم، خصوصاً:

1. مالك دورة حياة SQLite والمحرك وعميل LSP.
2. استراتيجية التخزين لتفضيلات التطبيق، ومصدرها الوحيد.
3. اختيار آلية اختيار المجلدات ومراقبة الملفات على كل منصة مستهدفة.
4. سياسة stale index وإعادة الإرسال بعد انقطاع LSP.
5. صيغة مقارنة مخرجات التمارين، وحدود التنفيذ التي يوفرها المحرك فعلياً.
6. أهداف التشغيل المدعومة لخادم LSP وكيفية توفير executable لها.

لا توسّع نطاق المرحلة إلى بناء المحرر أو إدخال محتوى الدروس؛ تُسجل تلك الأعمال
ضمن المراحل التالية في الخطة الرئيسية.
