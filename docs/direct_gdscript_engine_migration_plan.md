# الخطة التنفيذية للانتقال إلى `gdscript_engine` مباشرة

**الهدف:** تشغيل وتحليل وتحرير GDScript من التطبيق باستخدام `gdscript_engine`
مباشرةً، وإزالة `gdscript_lsp` وطبقة LSP كوسيطين بين التطبيق والمحرك.
**الحالة:** نُفذ الانتقال الأساسي إلى `gdscript_engine` مباشرةً. المتبقي هو
التحقق النهائي الشامل، وتوثيق حدود الوظائف التي لا يقدمها المحرك.
**النطاق:** تطبيق Flutter، اعتماد `gdscript_engine`، خدمات المحرر ومساحة العمل،
الواجهات والاختبارات والتوثيق المرتبط بها.
**المرجع المعماري الحالي:** [الخطة الرئيسية](./execution_plan.md) و[خطة
المرحلة الأولى](./phase_1_execution_plan.md).

---

## 1. النتيجة المطلوبة ومبدأ الانتقال

### سجل التنفيذ الحالي

- اكتمل نقل محرر الدروس والتمارين والتجربة السريعة ومحرر لوحة الرئيسية إلى
  واجهات المحرك للتشخيصات والتلوين، مع الإكمال في محرر التمرين.
- أصبحت مساحة العمل تكتشف ملفات GDScript محلياً، وتحفظ لقطات المشروع وتبحث
  فيها، وتعرض تشخيصات المحرك للمسودة النشطة دون تشغيل خادم أو عملية خارجية.
- أزيل حقن موفر LSP وشاشة تشخيصاته، وحذفت ملفات العميل والنقل والفهرسة
  والاختبارات التابعة لها، مع استبدال تغطية الاكتشاف والبحث باختبارات للمستودع.
- لا يوفر المحرك الحالي تنسيقاً آلياً أو بحثاً متعدد الملفات عن التعريفات
  والمراجع؛ أزيل إجراء التنسيق من المحرر ولا يُعلن عن دعم تلك الإمكانات.
- اجتازت الاختبارات المركزة للمستودع والمحرك والتمارين وتشخيصات الإعدادات.
  لم يكتمل تحقق المجموعة الكاملة بسبب تجاوز عرض في لوحة الرئيسية الضيقة؛
  والتحليل الساكن لم يسجل أخطاء بناء لكنه يعرض تحذيرات/معلومات موجودة.

يستورد التطبيق حزمة `gdscript_engine` ويستدعي واجهاتها مباشرةً داخل عملية Dart
للتنفيذ وخدمات المحرر. لا يشغّل التطبيق executable خاصاً بـ`gdscript_lsp`، ولا
ينشئ اتصال JSON-RPC/LSP، ولا يتطلب إعداد مسار executable أو اتصال مساحة عمل
حتى يعمل المحرر التعليمي.

لا يعني هذا الانتقال أن واجهة `EditorAPI` الحالية تغطي تلقائياً كل إمكانات LSP.
يبين README المحرك أنه يوفر تحليلاً وتشخيصات وتلويناً وإكمالاً وميزات تحرير
أخرى، لكنه ليس خادم LSP متوافقاً بالكامل مع Godot Editor. لذلك:

1. تُحفظ الوظائف التي يدعمها المحرك وتُربط مباشرةً بواجهاته الموثقة.
2. تُسجل الفجوات قبل حذف العميل الحالي، وتُستكمل بواجهات أصلية في المحرك أو
   بخدمات تطبيق محدودة تعتمد عليه.
3. لا تُحذف وظيفة ظاهرة للمستخدم ولا تتحول إلى نتيجة فارغة أو نجاح شكلي من
   دون قرار موثق واختبار قبول.
4. يكون نطاق المرحلة الأولى محرر الدروس التعليمي. وتبقى ميزات مساحة العمل
   متعددة الملفات رهناً ببوابة قرار صريحة قبل نقلها أو إيقافها.

## 2. خط الأساس قبل الانتقال (مرجع تاريخي)

> يصف هذا القسم البنية التي كانت قائمة قبل التنفيذ، ولا يمثل وصفاً للكود
> الحالي.

### التكامل الموجود

- `pubspec.yaml` يعتمد على `gdscript_engine` عبر مسار محلي
  `../gdscript_engine`.
- `CodeRunnerService` يملك `GDScriptEngine` بالفعل وينفذ الشيفرة التعليمية.
- `LanguageServerProvider` يشغّل عميل LSP، ويملك فتح المستندات وتشخيصاتها
  وإكمالها وتنسيقها وطلبات المحرر، كما يدير اتصال الخادم وفهرسة مساحة العمل.
- `LanguageServerFactory` وناقل LSP يحددان executable ويديران subprocess
  ورسائل البروتوكول.
- `LessonScreen` يربط فتح المستند ومزامنته وإظهار التحذيرات وحالة المحرر
  باتصال LSP.
- واجهات مساحة العمل والبحث والإعدادات تعرض حالات اتصال الخادم أو تعتمد عليها.
- الاختبارات الحالية تشمل اختبارات العميل والنقل والفهرسة وتكامل عملية LSP.

### قدرات المحرك ذات الصلة

تتضمن `GDScriptEngine.editorApi` الحالية، بحسب API المصدر وREADME المحرك،
واجهات لتحليل التشخيصات، والتلوين النحوي والدلالي، والإكمال، ومساعدة التواقيع،
ومعلومات hover، وتعريف الرموز داخل المستند، وطيّ الكود، ومطابقة الأقواس.
وتتيح `CompletionProjectContext` للمضيف تزويد المحرك بمسارات وبيانات سياق
المشروع المستخدمة في الإكمال.

لا تفترض الخطة وجود بدائل جاهزة في المحرك لما يلي: تنسيق المستند، تحليل
التعريفات والمراجع عبر ملفات متعددة، رموز مساحة العمل، البحث النصي الشامل،
مراقبة الملفات ومزامنة فهرس المشروع، أو كل إمكانات LSP الأخرى. تُثبت كل قدرة
مطلوبة بمراجعة API واختبار قبل الاعتماد عليها.

## 3. خريطة الاعتماد والمراحل

```text
0. تثبيت النطاق وخط الأساس
  → 1. تدقيق عقد المحرك والفجوات وتوافق المنصات
  → 2. توحيد ملكية المحرك وخدمات التطبيق
  → 3. نقل محرر الدروس إلى EditorAPI
  → 4. حسم ونقل وظائف مساحة العمل
  → 5. إزالة LSP والخادم من التطبيق
  → 6. التحقق الشامل والإطلاق
```

لا تبدأ إزالة LSP قبل اجتياز المرحلتين 1 و3، ولا تبدأ إزالة وظائف مساحة العمل
قبل اعتماد مخرجات المرحلة 4. لا يُشترط تشغيل جميع المراحل في إصدار واحد؛ يمكن
إطلاق المحرر التعليمي المباشر أولاً إذا كان ذلك متوافقاً مع سياسة المنتج.

## المرحلة 0: تثبيت النطاق وخط الأساس

**الهدف:** توثيق ما يعنيه «التعامل مباشرة» وتحديد السلوك الحالي الذي يجب
الحفاظ عليه.
**الاعتماد:** لا شيء.

### المهام

1. جرد جميع استدعاءات LSP في `lib/` و`test/`، وربط كل استدعاء بواجهة المستخدم
   والسلوك الذي يراه المستخدم.
2. تصنيف الوظائف إلى:
   - **تعليم وتشغيل:** تنفيذ أمثلة الدروس والتمارين، المخرجات والأخطاء.
   - **تحرير داخل الدرس:** التشخيصات، الإكمال، التلوين، hover، التواقيع،
     التنقل لتعريف محلي، الطيّ ومطابقة الأقواس والتنسيق.
   - **مساحة العمل:** الاتصال بجذر مشروع، اكتشاف الملفات ومزامنتها، تحرير
     ملفات متعددة، البحث النصي والرمزي.
3. تحديد أن المحرك سيُستخدم داخل عملية التطبيق، وأن تشغيل executable LSP أو
   استخدام JSON-RPC ليس مساراً احتياطياً.
4. حفظ خط أساس للاختبارات الحالية ذات الصلة، ونتائج المحلل والبناء للهدف
   المدعوم حالياً. فصل فشل البيئة أو التبعيات عن فشل السلوك.
5. توثيق المنصات المستهدفة فعلياً. لا تُعلن قابلية تشغيل المحرر أو المحرك على
   منصة لم تُبنَ وتُختبر.

### معيار الخروج

- كل استخدام مباشر أو غير مباشر لـLSP له مالك وسلوك مستهدف مسجل.
- حُددت المنصات والإمكانات التي يجب أن تبقى في أول إصدار بعد الانتقال.
- توجد نتائج خط أساس قابلة للمقارنة لاختبارات التنفيذ والمحرر.

## المرحلة 1: تدقيق عقد المحرك وسد الفجوات

**الهدف:** إثبات أن الواجهات المباشرة تغطي السلوك المطلوب، وتحديد أي تطوير
لازم في `gdscript_engine` قبل ربط الواجهات.
**يعتمد على:** المرحلة 0.

### المهام

1. تثبيت مصدر الاعتماد وإصداره/التزامه بوضوح. يستمر استخدام مسار `path` المحلي
   إذا ظل مناسباً لتطوير المشروع، مع توثيق شرط وجود المستودع الشقيق في بيئة
   البناء. لا تُضمَّن نسخة ثانية متباينة من المحرك داخل التطبيق.
2. إعداد مصفوفة تتبع لكل ميزة: سلوك LSP الحالي، API المحرك المقابل، التحويل
   المطلوب، ونتيجة الاختبار:

   | الميزة | مرشح API المباشر | السؤال الواجب حسمه |
   |---|---|---|
   | التنفيذ والمخرجات والتشخيصات | `GDScriptEngine.execute` | هل النتيجة وحدود التنفيذ مطابقة للحاجة؟ |
   | تشخيص الشيفرة أثناء الكتابة | `EditorAPI.getDiagnostics` | هل التشخيص متزامن، وما دقة المواقع والأنواع؟ |
   | التلوين النحوي والدلالي | `getSyntaxHighlights` و`getSemanticHighlights` | هل تحويل spans إلى صيغة المحرر يحافظ على UTF-16؟ |
   | إكمال الشيفرة وسياق المشروع | `getCompletions` و`CompletionProjectContext` | ما السياق المطلوب، وكيف تُحدّثه الخدمة؟ |
   | التواقيع وhover | `getSignatureHelp` و`getHoverInfo` | ما السلوك عند موضع المؤشر وحالات النص غير المكتمل؟ |
   | تعريف محلي وطيّ الكود وأقواسه | `findDefinition` و`getFoldingRanges` و`findMatchingBracket` | هل النطاق محلي للملف، وما تنسيق المواضع؟ |
   | التنسيق | لا يُفترض وجود بديل حتى يُثبت | هل يُضاف formatter للمحرك أم يُزال الإجراء من الواجهة؟ |
   | البحث والرموز عبر الملفات | لا يُفترض وجود API مكافئ | هل ينفذ المحرك فهرساً متعدد الملفات أم ينفذ التطبيق وظيفة محدودة؟ |
3. إنشاء اختبار عقد صغير على API المحرك للميزات التي ستستخدمها أولاً، بما
   فيها ملف صالح، ملف مع أخطاء، نص جزئي أثناء الكتابة، ومواقع مؤشر غير ASCII.
4. تحديد سياسة أداء التحليل أثناء الكتابة. قياس كلفة التحليل للمستندات الواقعية
   قبل وضع debounce أو cache؛ عدم إضافة آلية تخزين مؤقت إلا إذا أثبت القياس
   الحاجة وصحة الإبطال عند تغير النص.
5. فتح طلبات/تغييرات مستقلة في مستودع المحرك عند ثبوت فجوات لازمة، مع API
   typed واختبارات محرك وتوثيقها قبل اعتمادها في التطبيق.

### معيار الخروج

- لكل ميزة مطلوبة قرار: مدعومة مباشرة، تحتاج تطوير محرك، تُنفذ في التطبيق
  اعتماداً على المحرك، أو تُستبعد بقرار منتج معلن.
- لا تعتمد الواجهة على API تجريبي أو سلوك غير مثبت.
- حُسمت حدود الأداء والترميز وملكية موارد المحرك.

## المرحلة 2: توحيد ملكية المحرك وخدمات التطبيق

**الهدف:** جعل المحرك مورداً طويل العمر تملكه طبقة خدمات التطبيق، لا الواجهة،
وتوفير عقود typed قابلة للاختبار.
**يعتمد على:** المرحلة 1.

### المهام

1. مراجعة `CodeRunnerService` و`TestRunnerService` لمنع إنشاء محرك مكرر
   بلا حاجة، وتحديد إن كان `CodeRunnerService` سيبقى نقطة دخول التنفيذ
   والتحليل أم ستضاف إليه خدمة تحرير مستقلة.
2. توفير خدمة تطبيق للمحرر تمرر نص المستند وموضع المؤشر وتحوّل نتائج
   `EditorAPI` إلى نماذج التطبيق. لا تكشف أنواع JSON أو بروتوكول LSP إلى
   الواجهات.
3. جعل حقن `GDScriptEngine` ممكناً في الاختبارات، وتحديد مالك واحد فقط
   لاستدعاء `dispose`. ضمان أن الإغلاق لا يحدث قبل انتهاء العمليات الجارية،
   أو توثيق/اختبار سياسة الإغلاق المناسبة.
4. تحويل التشخيصات ونتائج الإكمال ومواضع التلوين والـhover إلى نماذج typed
   دون إسقاط الرسائل أو المواقع أو الشدة.
5. تحديث تركيب الاعتماديات في `AppDependencies` لإضافة خدمات المحرر المباشرة
   وضمان فشل التهيئة يظهر بوضوح بدلاً من حالة اتصال موهمة.
6. إبقاء تشغيل الكود التعليمي مستقلاً منطقياً عن طلبات التحرير، حتى لو تشاركا
   محركاً واحداً؛ اختبر عدم تداخل النتائج أو الحالة بين طلبات متتابعة.

### الاختبارات

- حقن محرك/واجهة بديلة أو fake عند اختبار الخدمة دون تشغيل خادم.
- نتائج تنفيذ ناجح وفاشل، diagnostics، إغلاق المورد، واستدعاء بعد الإغلاق.
- تحويل أنواع المحرك ومواضعه دون فقد معلومات أو افتراض نجاح.

### معيار الخروج

- كل واجهة خدمة مباشرة لها عقد typed واختبارات.
- لا تنشئ الشاشات محركاً خاصاً بها ولا تتخلص من مورد تملكه خدمة أخرى.

## المرحلة 3: نقل محرر الدروس إلى المحرك المباشر

**الهدف:** جعل تجربة تحرير الدروس تعمل دون اتصال LSP أو إعداد مساحة عمل.
**يعتمد على:** المرحلة 2.

### المهام

1. تحديث `LessonScreen` لإزالة فتح/مزامنة مستند LSP والتحذيرات وحالة الاتصال
   من مسار تحميل الدرس. تمرير تغييرات النص إلى خدمة المحرر المباشرة.
2. ربط ميزات الواجهة بما ثبت دعمه في المرحلة 1:
   - عرض diagnostics أثناء التحرير مع مواضعها ورسائلها الحقيقية.
   - عرض الإكمال وقبول النص المقترح في موضع المؤشر الصحيح.
   - تطبيق التلوين النحوي والدلالي باتفاقية offsets موحدة.
   - عرض hover ومساعدة التوقيع حيث تدعمهما واجهة المحرر.
   - دعم الطيّ ومطابقة الأقواس والتنقل المحلي عند ثبوت صلاحية الموقع.
3. مراجعة `CodeEditorWidget` وواجهات سطح المكتب/الهاتف لضمان نفس السلوك
   والعقود، وإبقاء اتجاه إدخال/عرض الكود LTR مع تعريب الرسائل المحيطة.
4. عدم استدعاء التنفيذ الكامل لكل ضغطة مفتاح بغرض التشخيص إذا كان للمحرك
   تحليل تحرير مستقل؛ استخدم API التحرير المخصص، واستخدم `execute` فقط عند
   طلب تشغيل المثال أو الاختبار.
5. معالجة النصوص غير المكتملة بصورة طبيعية كمحرر، دون استثناءات غير ممسوكة
   أو تشخيصات قديمة بعد تغيير النص.
6. إضافة حالات loading/error فقط عند وجود عملية غير متزامنة حقيقية. نتائج
   API المتزامنة لا تعرض حالة اتصال أو انتظار مصطنعة.

### الاختبارات

- تحميل درس وتشغيل المثال دون إعداد executable أو اختيار مجلد عمل.
- تغيير الشيفرة وتحديث diagnostics والتلوين والإكمال وفق واجهات المحرك.
- قبول الإكمال عند بداية/وسط/نهاية السطر ومع نص عربي مجاور.
- إغلاق الدرس والتبديل السريع بين الدروس دون نتائج قديمة أو موارد معلقة.
- اختبارات widget للمحرر على التخطيطات المعتمدة.

### معيار الخروج

- يتوفر المحرر التعليمي ووظائفه المتفق عليها من دون `LanguageServerProvider`.
- لا يبدأ التطبيق أو الدرس subprocess عند فتح الدرس أو الكتابة أو طلب الإكمال.

## المرحلة 4: حسم ونقل وظائف مساحة العمل

**الهدف:** تقرير مصير تحرير المشاريع متعددة الملفات والبحث والفهرسة دون
الاعتماد على إمكانات LSP غير الموجودة في المحرك.
**يعتمد على:** المرحلة 1، ويمكن تنفيذ أجزاء التطبيق بعد المرحلة 2.

### بوابة قرار إلزامية

اختر ووثق مساراً لكل وظيفة في مساحة العمل قبل حذف العميل:

1. **نقلها إلى المحرك:** تطوير واجهات typed وفهرسة/تحليل متعدد الملفات في
   `gdscript_engine`، بما في ذلك تحديث الملفات وإزالة القديم عند الحاجة.
2. **خدمة مضيفة للتطبيق:** استخدام اكتشاف الملفات المملوك للتطبيق، ثم تقديم
   البحث النصي أو الرموز المطلوبة بوصفها وظيفة تطبيق واضحة؛ لا تنسب هذه
   القدرات إلى المحرك إن لم يوفرها.
3. **تضييق النطاق:** حذف أو تعطيل الوظيفة ومسار الوصول إليها في الواجهة
   بتغيير منتج صريح، وتحديث التوثيق والتعريب والاختبارات.

لا يُقبل إبقاء زر بحث/تنسيق/تعريف متعدد الملفات يعمل ظاهرياً ثم يرجع قائمة
فارغة لمجرد عدم وجود API مطابق.

### المهام المشتركة

- إن بقيت مساحة العمل: احتفظ بملكية التطبيق لاكتشاف الملفات، حدود الحجم،
  الروابط الرمزية، المجلدات المستثناة، صلاحيات القراءة، المسارات النسبية،
  وتزامن المسودات والحفظ والحذف.
- مرر `CompletionProjectContext` للمحرك من لقطة بيانات موثقة ومحدودة. حدّث
  السياق بعد تغيير الملفات أو جذر المشروع، ولا تجعل المحرك يقرأ القرص ضمنياً.
- حدد التمييز بين مسارات `res://` ومسارات النظام في عرض وإدخال المسارات.
- اختبر أن ملفاً خارج الجذر أو رابطاً رمزياً غير مسموح لا يدخل السياق.
- إذا احتاجت وظيفة بحث أو فهرسة إلى عملية بطيئة، اعرض أخطاء القراءة بوضوح
  وحدد الإلغاء وحدود الحمل.

### معيار الخروج

- لكل ميزة مساحة عمل قرار منتج وتنفيذ واختبارات قبول.
- لا تعتمد واجهة مساحة العمل على خادم حي أو بروتوكول LSP.
- لا تضيع المسودات أو تُعرض نتائج فهرسة قديمة على أنها حديثة.

## المرحلة 5: إزالة LSP وخادم اللغة من التطبيق — مكتملة

**الهدف:** حذف المسار الوسيط بعد أن أصبحت كل الوظائف المعتمدة مباشرة أو
حُسم إيقافها.
**يعتمد على:** اجتياز المرحلتين 3 و4.

### المهام

1. إزالة حقن `LanguageServerProvider` من `AppDependencies` و`app.dart`
   ودورة حياة `disconnect` التابعة له.
2. إزالة `LanguageServerProvider` وعميل LSP وناقل العملية والمصنع وفهرس
   مساحة العمل الخاص ببروتوكول LSP، بعد نقل أي مسؤولية لازمة إلى المالك
   الجديد.
3. تحديث الشاشات التي تعرض الاتصال أو حالة LSP، بما فيها مساحة العمل والبحث
   والإعدادات والدرس، وإزالة حقل مسار executable وأي تعليمات ضبط بيئية لم تعد
   مطلوبة.
4. إزالة اختبارات LSP/process/integration واستبدالها باختبارات الخدمة المباشرة
   واختبارات ميزات مساحة العمل التي تقرر الإبقاء عليها. لا تحذف اختبارات
   سلوك صالح قبل نقل تغطيتها.
5. إزالة أي ملفات ترجمة لا تعود مستخدمة، وتحديث ملفات ARB ثم تشغيل مولد
   الترجمة بالطريقة المتبعة في المشروع.
6. التحقق من أنه لا توجد مراجع شيفرة أو توثيق تشغيلية إلى `gdscript_lsp`،
   إعداد executable، LSP، JSON-RPC أو subprocess. يمكن إبقاء ذكر تاريخي
   مختصر في سجل انتقال إذا كان مفيداً، لكن لا يبقى مسار تشغيل نشط.
7. تحديث [الخطة الرئيسية](./execution_plan.md) و[خطة المرحلة
   الأولى](./phase_1_execution_plan.md) والمستندات الوظيفية ذات الصلة لتعكس
   المعمارية الجديدة، مع عدم تغيير تاريخ ما نُفذ سابقاً.

### معيار الخروج

- لا يعتمد التطبيق على حزمة أو executable أو اتصال `gdscript_lsp`.
- بحث ثابت في الشيفرة والاعتمادات لا يجد مسار تشغيل LSP متبقياً.
- لا توجد عناصر واجهة تَعِد بميزة حُذفت أو لم تُنفذ.

## المرحلة 6: التحقق والإطلاق

**الهدف:** إثبات اكتمال الانتقال على المنصات المدعومة وحفظ السلوك التعليمي.
**يعتمد على:** المرحلة 5.

**الحالة الحالية:** الاختبارات المركزة ناجحة. يلزم معالجة تجاوز عرض واجهة
لوحة الرئيسية على العرض الضيق، ثم إعادة الاختبارات الكاملة وتشغيل بناء المنصة
المستهدفة قبل إعلان الإطلاق.

### التحقق

1. تشغيل تنسيق Dart والتحليل الساكن واختبارات الخدمات والمحرر المستهدفة.
2. تشغيل مجموعة Flutter الاختبارية كاملة بعد نجاح الاختبارات الموجهة.
3. بناء وتشغيل التطبيق على كل منصة معلنة، مع التحقق خصوصاً من توافر اعتماد
   المحرك الأصلي/الـFFI إن كانت واجهاته تستخدمه على المنصة.
4. اختبار سيناريو يدوي من فتح درس إلى تعديل الكود وتشغيل المثال وعرض الخطأ
   وإكمال تمرين وحفظ التقدم، من دون إعداد LSP أو شبكة.
5. اختبار مساحة العمل والبحث فقط للوظائف التي حُسم الإبقاء عليها في المرحلة 4.
6. فحص السجلات للتأكد من عدم ابتلاع أخطاء المحرك أو إظهار نجاح كاذب، وعدم
   تسريب محتوى الشيفرة في السجلات.
7. تسجيل المنصات والميزات غير المختبرة صراحةً في ملاحظات الإصدار.

### معيار الخروج

- ينجح التحليل والاختبارات والبناء المستهدف، أو تُوثق موانع بيئية محددة ولا
  تُخلط بادعاء نجاح.
- يعمل مسار الدرس الكامل دون LSP، وكل ميزة متبقية في المنتج لها اختبار قبول.
- وُثقت حدود المحرك المعروفة وتجربة التعطل/الخطأ بما يتوافق مع الواقع.

## 4. المخاطر ومعالجتها

| الخطر | الأثر | المعالجة |
|---|---|---|
| واجهة المحرك لا تغطي كل طلبات LSP | فقد قدرات المحرر أو مساحة العمل | تدقيق عقد واختبار قبل الحذف، ثم تطوير المحرك أو قرار نطاق معلن |
| اختلاف صيغة المواقع أو وحدات offsets | وضع التشخيص أو الإكمال في موضع خاطئ | عقد موحد واختبارات UTF-16 ونصوص متعددة اللغات |
| ثقل التحليل أثناء الكتابة | تأخر واجهة المحرر | قياس على شيفرات واقعية وتحسين المحرك أو جدولة الطلبات عند ثبوت المشكلة |
| امتلاك أكثر من خدمة للمحرك نفسه | تسرب أو إغلاق مبكر أو تداخل نتيجة | مالك واحد لدورة الحياة واختبارات حقن/إغلاق |
| اعتماد المحرك المحلي غير متاح في CI أو جهاز مطور | فشل حل الاعتمادات أو البناء | توثيق مصدر الاعتماد وإعداده في CI وتثبيت إصدار/التزام معروف |
| الإبقاء على مساحة العمل دون API متعدد الملفات | نتائج بحث أو تنقل أقل من الحالية | قرار صريح بشأن البحث المضيف أو تضييق المنتج قبل إزالة LSP |
| اختلاف دعم المنصات بسبب FFI | فشل البناء أو التشغيل على هدف | بناء فعلي لكل هدف وعدم ادعاء دعم غير متحقق |

## 5. شروط عدم القبول

- لا تُترك واجهة المستخدم معتمدة على حالة «متصل» حتى تعمل ميزات الدرس.
- لا يُستخدم `gdscript_lsp` كـfallback عند فشل المحرك، ولا يُخفى هذا المسار.
- لا تُستبدل ميزات غير مدعومة بمخرجات فارغة أو رسائل نجاح.
- لا تُحذف مسؤولية اكتشاف الملفات أو حفظ المسودات قبل تحديد مالكها الجديد.
- لا تُدمج تعديلات مستودع المحرك مع التطبيق على أساس API غير مستقر أو غير
  مختبر.
- لا يُعلن اكتمال الانتقال اعتماداً على نجاح التنفيذ فقط؛ معيار النجاح يشمل
  خدمات التحرير ومساحة العمل التي قرر المنتج الاحتفاظ بها.
